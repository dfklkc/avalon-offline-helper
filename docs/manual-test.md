# 多人手工测试

领域单元测试不能代替真实 OpenID、云数据库权限和多人并发验证。本清单用于体验版或正式发布前的端到端验收。

## 测试准备

至少准备：

- 1 个与项目匹配的真实小程序 AppID；
- 1 个已关联 AppID 的 CloudBase 文档型数据库环境；
- 已部署到同一环境的 `gameApi`；
- `rooms` 和 `room_secrets` 集合，两者均为“仅管理端可读写”；
- 至少 5 个不同的真实微信账号；
- 足够的手机，或微信开发者工具 + 多部手机的组合。

多个页面或开发者工具中的多个模拟器不一定代表不同 OpenID。发牌和投票测试必须以不同真实微信账号为准。

## 1. 部署前静态检查

```bash
npm test
npm run check
```

预期：

- 命令退出码为 0；
- 5–10 人角色和任务规则测试通过；
- 小程序页面与云函数脚本无语法错误。

## 2. 环境和权限冒烟测试

1. 编译小程序，确认没有 `invalid env`、`Cloud API isn't enabled` 或 `function not exists`。
2. 在客户端调试控制台执行：

```js
wx.cloud.database().collection('rooms').get()
wx.cloud.database().collection('room_secrets').get()
```

3. 两次请求都应返回权限拒绝。
4. 回到小程序正常创建房间，应成功，证明 `gameApi` 仍能以管理端身份读写。

失败判定：任一集合能在客户端直接读取，都必须停止发布并修正权限。

## 3. 建房和加房

1. 账号 A 输入合法昵称并创建房间。
2. 记录 6 位房间码，确认不包含容易混淆的字符。
3. 账号 B–E 依次使用正确房间码加入。
4. 每次加入后，其他已在房间页的设备应在 0–5 秒内显示新成员。
5. 输入错误、不完整或不存在的房间码，应给出可理解的提示，不应创建脏数据。
6. 输入空昵称、纯空白或超过长度上限的昵称，应被拒绝。
7. 同一账号重复进入同一房间，不应生成第二个座位。
8. 非房主设备不应看到或成功执行房主专用操作。

## 4. 5 秒单快照轮询

当前实现不使用 `watch`，本项必须单独验收：

1. 保持 A–E 全部在房间页前台。
2. A 执行一次会改变房间状态的操作。
3. 记录最慢一台设备出现新状态的时间，正常应不超过一个 5 秒周期加网络余量。
4. 将 E 切到后台 30 秒，期间进行数次操作；确认 E 后台期间不持续高频请求。
5. E 回到前台后应立即或在下一个轮询周期恢复最新快照。
6. 反复进出房间页 5 次，云函数日志中不应出现成倍增长的重复轮询。

不要把 0–5 秒更新误写为“已启用实时推送”。

## 5. 开局和秘密发牌

1. 人数少于 5 时，开局必须失败。
2. 只有房主能开始游戏。
3. 达到 5 人后，分别测试新手配置和经典配置。
4. 每个账号只能看到自己的角色、阵营和应知信息。
5. 在开发者工具 Network、Console 和 `gameApi` 返回值中搜索其他玩家的角色，不应找到整份分配。
6. 梅林应看到除莫德雷德外的邪恶玩家；派西维尔应看到梅林/莫甘娜候选但无法分辨；奥伯伦与其他邪恶玩家互不可见。
7. 刷新、切后台再返回后，当前账号仍只能看到同一份自己的角色。

安全测试结束后，可由一名不参与当局的管理员在控制台检查 `room_secrets` 中的阵营数量是否正确。游戏中的参与者不应做该检查。

### 规则速览与本人角色详解

1. 从小程序提供的入口打开规则速览，确认 5–10 人的五轮队伍人数和失败阈值与本文后面的回归矩阵一致。
2. 速览页可以展示通用角色说明，但页面加载不应请求当前房间的 `room_secrets`。
3. 在未开局、已开局和游戏结束三种状态打开速览页，页面不得出现“某个玩家实际是某角色”的信息。
4. 每个账号打开本人身份页，揭示后应显示自己的角色名、阵营、详细说明和按规则应知的玩家。
5. 检查本人身份页的 Network 响应和页面 `data`：除了当前角色视野必须的玩家列表，不应包含其他玩家的角色 key、阵营或完整角色说明。
6. 遮住身份、切到后台或离开页面时，已揭示的角色与视野应从页面数据中清除；返回后需重新显式揭示。

## 6. 组队与组队投票

1. 只有当前队长能提名队伍。
2. 队伍人数必须与当前轮次匹配；重复成员或房间外成员必须被拒绝。
3. 每位玩家只能提交一次组队票。
4. 在全部选票收齐前，其他玩家不能看到任何人的具体选择。
5. 最后一票提交后才显示汇总结果和每位玩家的赞成/反对选择。
6. 本轮结算后，重新刷新所有设备，逐人组队票应对房间成员一致可见。
7. 进入下一轮并完成另一次组队票，投票历史应按轮分开统计，上一轮的逐人结果不被覆盖。
8. 组队票必须严格过半；平票为否决。
9. 两台设备同时点击提交，计数不应丢失、重复或提前结算。
10. 组队通过和否决后，下一阶段、队长或否决轮数应按规则变化。

## 7. 任务投票和结算

1. 只有当前任务队成员能提交任务票。
2. 善良玩家不能成功提交失败票，即使客户端手工构造请求。
3. 邪恶玩家可选择成功或失败。
4. 任务票未收齐前不能显示单人选择或推导出选择的信息。
5. 结算后只显示汇总的成功/失败数和任务结果，不对应到具体玩家。
6. 5–6 人的每轮任务有 1 张失败票即失败。
7. 7–10 人的第 4 轮任务需要 2 张失败票才失败；只有 1 张失败票时任务仍成功。
8. 两名队员同时提交最后两票，应只结算一次。

额外隐私检查：任务结算后检查房间快照、页面数据、Network 返回值和云函数日志，只允许出现成功/失败总数，不得出现任务票与 `playerId`、昵称、座位或 OpenID 的对应关系。

## 8. 私人玩家标记和文字备注

1. 账号 A 选择玩家 B，设置一个私人标记并输入一段易识别的文字，例如“A-only-731”。
2. 保存时确认客户端调用 `gameApi` 的 `savePlayerNote` action，而不是直接写数据库。
3. A 等待一次轮询并刷新页面，标记和备注仍存在。
4. 账号 B–E 分别进入相同页面，任何账号都不应看到“A-only-731”。
5. 在 B–E 的 Network、Console、页面 `data` 和 `getState` 原始返回值中搜索“A-only-731”，结果必须为空。
6. B 为同一个目标玩家保存“B-only-924”；A 仍只看到自己的“A-only-731”，B 只看到“B-only-924”。
7. A 修改对其他多名玩家的标记，房间快照中的 `privateView.playerNotes` 只包含 A 自己的备注映射。
8. 手工伪造 `ownerOpenid`、`authorPlayerId` 或其他所有者字段再调用 `savePlayerNote`，应被忽略或拒绝，不得改变其他账号的备注。
9. 传入房间外的 `targetPlayerId`、非法标记值或超长文字，服务端应拒绝或按明确上限安全截断。
10. 在云函数日志中搜索上述测试备注，日志不应记录备注正文或完整 `notesByPlayer`。

## 9. 重连、异常和恢复

1. 一名玩家断网 30 秒，其他人继续操作；恢复网络后应拉取当前最新快照。
2. 完全关闭小程序后从最近使用重新进入，测试当前实现所提供的房间恢复行为。
3. 在云函数返回失败、超时或断网时，界面应显示可理解的错误，不应将本地乐观状态当作服务端已成功。
4. 连续快速点击同一提交按钮，服务端应拒绝重复操作，界面不应卡在永久加载。
5. 在控制台查看云函数错误日志，日志不应包含整副角色分配、未公布选票或其他玩家的私密快照。

## 10. 恶意参数和越权测试

使用微信开发者工具调用 `wx.cloud.callFunction`，手工增加伪造的 `openid`、`playerId`、房主标志、他人座位或非法阶段参数。预期：

- 伪造 OpenID 不改变云函数从 `getWXContext()` 获取的真实身份；
- 非房间成员不能读取房间快照；
- 房间成员不能请求他人角色；
- 房间成员不能读取或改写他人的 `notesByPlayer`；
- 非房主/非队长不能执行特权操作；
- 已结算或错误阶段的投票被拒绝；
- 任何失败都不返回数据库文档全文或服务端堆栈给普通用户。

## 12. 发布门禁

以下任一项不满足时不应发布：

- 两个数据库集合未设为仅管理端可读写；
- 任一玩家能看到他人角色或未公布选票；
- 任一玩家能看到或修改他人的私人标记/文字备注；
- 组队票在本轮结算前泄露，或结算后没有按轮保留逐人结果；
- 任务票暴露了任何玩家与成功/失败选择的对应关系；
- 伪造客户端身份可导致越权；
- 并发提交会丢票、重复结算或跳过阶段；
- 页面进入后台仍持续轮询，或重进页面后轮询计时器倍增；
- 云环境仍使用未明确续费/升级的免费体验计划。

> 截至 2026-08-23，免费体验环境只适合开发和内测。小程序正式上线后，该环境的到期时间会变更为上线后第 15 天，不能视为永久免费生产服务。见 [CloudBase 资源点价格文档](https://cloud.tencent.com/document/product/876/127357)。
